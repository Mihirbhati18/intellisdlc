The one big idea

Everything hangs off a requirement

Most project tools keep your requirements in one place, your bugs in another, and your test results somewhere else again. IntelliSDLC links them all to a single spine, so you can ask one question and actually get an answer: is this requirement really finished?

A requirement is a thing the software must do — “customers can pay by card at checkout”. It gets a code like REQ-103. Every other record in the system points back at one of these codes: the tasks built for it, the test cases that check it, the bugs found in it, and the releases that shipped it.

Because those links exist in the database, the software can work out the answer itself rather than asking a human to keep a spreadsheet up to date.

The two halves

A server that knows things, a page that shows them

The project is two programs that run at the same time and talk over the network, even though both are on your laptop.

The backend — port 8000

Written in Python with FastAPI. It owns the database and all the rules. It is the only thing allowed to decide whether you may edit a task, what a sprint’s risk score is, or which requirements have no tests. It speaks only JSON — no web pages.

  • models.py — defines the 12 database tables
  • routers/ — the web addresses (login, requirements, sprints, …)
  • services/ — the thinking: traceability, risk, the AI agent
  • security.py — password hashing and token checks
  • seed.py — the demo project it creates on first run

The frontend — port 5173

Written in TypeScript with React, served by Vite. It owns everything you see and nothing you trust. It draws tables, charts and forms, and asks the backend for every number on screen. If it hid a button it shouldn’t have, the backend would still refuse the action.

Why the split matters

Hiding a button is a convenience, not a security control. Every permission in IntelliSDLC is enforced on the server, and the test suite proves it by calling the API directly as a developer and checking it gets refused.

A click, start to finish

What really happens when you open the dashboard

  1. 1

    You sign in. The browser sends your email and password once. The backend compares the password against a bcrypt hash — the real password is never stored, only a one-way scramble of it.

  2. 2

    You get a token. A signed JWT that says who you are and what role you have, valid for 12 hours. The browser keeps it and attaches it to every later request automatically.

  3. 3

    The page asks for data. Opening the dashboard fires GET /api/v1/dashboard?project_id=1.

  4. 4

    The backend checks the token, then the rule. First “who are you?”, then “is this allowed for your role?”. A developer asking to run the risk predictor is refused here with a 403.

  5. 5

    It counts and replies. One JSON object with the headline numbers and both chart series — so the dashboard is a single round trip, not twelve.

  6. 6

    React draws it. Numbers into the tiles, arrays into the bar charts. If the token had expired, the browser would have cleared it and bounced you to the login page instead.

The versioning rule

Change a requirement’s title, description, priority or status and the backend bumps its version number and writes a history row describing the change, such as priority: HIGH → CRITICAL. Change anything else and no version is cut, so the history stays meaningful instead of filling with noise.

This is why REQ-103 sits at v3 in the demo: it was raised to CRITICAL and then moved into development, both during the live sprint. Those same two edits are what the risk predictor later counts as scope churn.

Traceability matrix

Feature one · derived, never typed

For every requirement the service works out five stages from the links in the database, then reduces them to one verdict.

StageHow it is decided
DesignedA design reference is recorded, or a design task is finished
ImplementedHow many development tasks are done — none, some, or all
TestedNo tests at all / any failing / all passing / still pending
BugsOpen bug count, and how many of those are critical
DeployedThe furthest environment a successful release reached

Those five collapse into the overall verdict:

Every stage satisfied and shipped to production

In the demo, only REQ-101 — login — qualifies.

COMPLETE

A test is failing, or a critical bug is open

REQ-103 hits both: TC-103 failed and two critical bugs are open.

AT RISK

Still on its way, nothing alarming yet

REQ-106 has no test cases written at all.

INCOMPLETE

Coverage is simply 20% per satisfied stage, so a requirement reading 100% is one that is designed, built, passing, bug-free and in production.

Why this is the useful bit

Mark one new test case as passed and the matrix changes on the next page load — the “without tests” count drops immediately. Nothing is cached and no one maintains it by hand.

Sprint risk predictor

Feature two · machine learning, with its working shown

Press Predict risk and the backend runs five steps. They are numbered to match the data-flow diagram in the project report.

Every one is counted from the database at that moment. The values shown are Sprint 3 in the demo.

The model

A logistic regression — the simplest honest choice for a yes/no question like “will this sprint slip?”. It is trained once by ml/train_model.py on 2,000 example sprints, saved to a file, and loaded when the backend starts. Scores below 40 are LOW, below 70 MEDIUM, and above that HIGH.

How it explains itself

This is the part worth understanding. Each of the ten numbers is standardised and multiplied by the weight the model learned for it. That product is how much that one factor pushed this score up or down. The top three are shown as a bar chart with a suggested action each. The chart is not decoration — it is the arithmetic behind the number.

For Sprint 3 that comes out at 89, HIGH, driven by the two critical bugs, a completion ratio of 0.25, and the scope changes mid-sprint. Sprint 4, with no bugs and plenty of time, scores 19, LOW.

Be straight about this in a viva

The 2,000 training sprints are synthetic — generated from a formula written for the project. The model therefore largely learned that formula back. The pipeline, the live feature extraction and the explainability are all genuine, but the reported accuracy of 0.735 describes synthetic data and is not evidence about real sprints. Saying so first is a much stronger answer than being asked.

AI project agent

Feature three · works with no internet

A chat box that answers questions about the project. It runs six steps, again numbered to match the report.

  1. 8.1

    Take the question.

  2. 8.2

    Sort it into a topic by keywords — bugs, tests, sprints, requirements, releases, risk or traceability. More specific topics win ties, so “what is the risk of the active sprint” is treated as a risk question, not a sprint one.

  3. 8.3

    Fetch only the relevant records, capped at 30 of each kind.

  4. 8.4

    Clean them. Password hashes and API keys are dropped entirely, email addresses are masked, and anything shaped like a secret key is replaced.

  5. 8.5

    Answer. With a Gemini key configured it asks Gemini, instructed to use only the supplied records and cite IDs. With no key — or if the call fails — it falls back to offline mode and composes the answer from the records itself.

  6. 8.6

    Return the answer with a badge saying which mode produced it and which records it used.

Offline mode is the default and the demo never needs a network. Ask “which critical bugs are still open?” and it replies with BUG-101 and BUG-103 by name, because it read them out of the database rather than inventing them.

Many projects

Added after the first build

The system holds any number of projects side by side. The Projects page creates and lists them; the switcher at the top of the sidebar changes which one you are working in, and the choice is remembered when you sign back in.

Every page — requirements, sprints, bugs, tests, releases, the dashboard, the matrix, the predictor and the chat — is scoped to the open project, so two projects never see each other’s data. A new project starts genuinely empty, and you fill it from the normal pages.

How it is tested

134 automated checks

SuiteChecksWhat it proves
pytest21Login and refusals, role permissions, the versioning rule, the three traceability verdicts, Sprint 3 HIGH and Sprint 4 LOW, redaction, the offline agent
drive.mjs84Every page clicked through in a real browser as both a manager and a developer
drive-projects.mjs16Creates a second project through the UI and proves the data stays separate
drive-edge.mjs13Expired tokens, empty states, a QA write flowing into the matrix

The browser suites drive headless Chrome over the DevTools Protocol with no testing library at all — Node’s built-in WebSocket is enough. They assert on what is actually on screen and fail if the console logs an error.

That matters because they caught real defects that the unit tests could not see: a traceability column pushed off the right edge of the screen, badges wrapping mid-word, an unhelpful error message when the backend was down, and a redirect that fired before data had loaded.

Real vs demonstration

The part worth knowing before anyone asks

The demo data is seed data, not hard-coded logic. Clear it out, enter your own project, and the machinery below keeps working. But not everything is equally real.

Genuinely working

  • The database, the links between records, and all the CRUD
  • The traceability matrix — computed from your data, nothing special-cased
  • Role permissions, enforced server-side
  • Requirement versioning with real change summaries
  • The offline AI agent, which genuinely reads your records
  • Multiple projects with properly isolated data

Demonstration only

  • The risk model’s training data is synthetic, so the score on a real sprint would be computed from chosen weights, not learned reality
  • Nothing reads your source code. No git, no CI, no repository link
  • Sign-in is demo-grade: tokens in browser storage, no refresh, no registration or password reset, no rate limiting
  • SQLite with no pagination — fine for a class project, not for thousands of records

The honest gap

“Implemented: 3/3” means a person ticked three tasks. “Build failure rate 0.25” means someone typed four release rows, one marked failed. Every signal is self-reported, so the matrix is exactly as truthful as the people updating it. A production tool closes that loop by reading commits from git and build results from CI — that integration, not more screens, is what would make this real.

Running it

Two terminals

cd backend
.venv\Scripts\activate
uvicorn app.main:app --reload        # http://localhost:8000/docs

cd frontend
npm run dev                          # http://localhost:5173

The database builds and seeds itself the first time the backend starts. To rebuild the demo data from scratch, run python -m app.seed --reset. Sign in with pm@intellisdlc.dev and Demo@123, or use the quick-fill buttons on the login page.
